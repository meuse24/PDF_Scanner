ZIEL
────
Drei PDF-Editierfunktionen in die bestehende „Ablage"-Ansicht integrieren:
  • Merge   — Mehrere PDFs zu einem neuen zusammenführen (Bulk-Aktion, ≥2 Auswahl)
  • Split   — Ein PDF visuell an gewählten Seiten aufteilen (Einzelaktion)
  • Reorder — Seiten innerhalb eines PDFs per Drag & Drop neu anordnen (Einzelaktion)

Technologische Basis: PdfBox-Android ist bereits integriert (2.0.27.0).
Neue Abhängigkeit: sh.calvin.reorderable (Compose Drag & Drop, s. Schritt 11)

SCHRITT 1 — Neue Utility-Klasse: PdfEditor.kt
================================================================================

Datei: util/PdfEditor.kt
Annotation: @Singleton (Hilt)

Alle Methoden sind NICHT suspend — reiner Dateisystem-Code, Aufrufer (ViewModel)
ist für den IO-Dispatcher verantwortlich. Kein UI-Thread-Kontakt.

  1.1  mergePdfs(inputs: List<File>, output: File)
       ─────────────────────────────────────────────
       - PDDocument.load() für jedes input-File in use{}-Block
       - PDFMergerUtility für korrekte Erhaltung von Lesezeichen, Metadaten
         und vorhandenem Text-Layer (bevorzugt gegenüber manuellem addPage)
       - Speichert in temporäre Datei im gleichen Verzeichnis wie output
       - Files.move(temp, output, ATOMIC_MOVE, REPLACE_EXISTING)
       - FEHLERBEHANDLUNG: Wenn move fehlschlägt (z.B. Datei durch FileProvider
         gesperrt), temp-Datei löschen und IOException mit Klartextmeldung werfen

  1.2  splitPdf(input: File, outputDir: File, splitAtPages: List<Int>): List<File>
       ─────────────────────────────────────────────────────────────────────────────
       - splitAtPages = 0-basierte Seitenindizes, an denen getrennt wird
         Bsp.: [2, 4] bei 6 Seiten → Teile: [0-1], [2-3], [4-5]
       - input-Dokument EINMAL laden, alle Teilgruppen daraus entnehmen
         (nicht für jede Gruppe neu öffnen → Speichereffizienz)
       - Für jede Teilgruppe: neues PDDocument, addPage() aus Quell-Doc
         (addPage kopiert Seitenreferenz, keine Pixeldaten im RAM)
       - Ausgabedateien: "${input.nameWithoutExtension}_Teil1.pdf" etc.
         Duplikat-Auflösung: _Teil1_2, _Teil1_3, …
       - Gibt Liste der erzeugten Files zurück

  1.3  reorderPages(input: File, newOrder: List<Int>, saveAsCopy: Boolean): File
       ─────────────────────────────────────────────────────────────────────────
       - newOrder = Permutation der Seitenindizes [0..n-1]
       - Neues PDDocument, addPage() in der gewünschten Reihenfolge
       - PdfBox erhält das OCR-Text-Layer beim Verschieben via addPage() korrekt
         → isSearchable muss NICHT zurückgesetzt werden
       - saveAsCopy = false: Temp-File → Files.move zu input (REPLACE_EXISTING)
         saveAsCopy = true:  Neue Datei mit Suffix „_Sortiert" anlegen
       - Gibt die Zieldatei zurück (input selbst oder neue Kopie)

  1.4  generateThumbnail(pdfFile: File, outputFile: File): Boolean
       ─────────────────────────────────────────────────────────────
       - MUSS auf Dispatchers.IO aufgerufen werden (PdfRenderer blockiert)
       - PdfRenderer → Seite 0 → 200×283 px Bitmap (A4-Verhältnis)
       - ARGB_8888, weißer Hintergrund (erase Canvas vor renderPage)
       - Als JPEG (85% Qualität) in outputFile schreiben
       - Bitmap nach Schreiben recyclen
       - Gibt true zurück bei Erfolg, false bei Fehler
       - Wird nach Merge, Split und reorderPages(saveAsCopy=true) aufgerufen

  1.5  renderPageThumbnail(pdfFile: File, pageIndex: Int, sizePx: Int): Bitmap?
       ────────────────────────────────────────────────────────────────────────
       - Rendert eine einzelne Seite als quadratisches Bitmap (sizePx × sizePx)
       - Hält keinen PdfRenderer zwischen Aufrufen offen (Ressource-Safety)
       - Wird vom ReorderViewModel und SplitViewModel zur Seiten-Vorschau genutzt
       - Gibt null zurück bei Fehler

SCHRITT 3 — ViewModel-Erweiterungen: HomeViewModel.kt
================================================================================

Neue StateFlows:
  private val _editLoading  = MutableStateFlow(false)
  val editLoading: StateFlow<Boolean> = _editLoading.asStateFlow()

  private val _editProgress = MutableStateFlow<Pair<Int,Int>?>(null)
  val editProgress: StateFlow<Pair<Int,Int>?> = _editProgress.asStateFlow()

WICHTIG: Alle Operationen laufen auf Dispatchers.IO (withContext(Dispatchers.IO)).
viewModelScope reicht für v1 aus (konsistent mit bestehendem OCR-Pattern).
Langfristig: WorkManager als robustere Alternative (App kann in Hintergrund).

  3.1  fun mergePdfs(records: List<ScanRecord>, outputFilename: String)
       ─────────────────────────────────────────────────────────────────
       - _editLoading = true
       - withContext(Dispatchers.IO):
           · Zieldatei: context.filesDir/scans/${outputFilename}.pdf
           · pdfEditor.mergePdfs(records.map { File(it.filepath) }, destFile)
           · pdfEditor.generateThumbnail(destFile, thumbFile)
           · Neuen ScanRecord anlegen (pageCount = Summe aller pageCount)
           · repository.saveScan(newRecord)
       - _success = getString(R.string.merge_success, outputFilename)
       - _editLoading = false
       - Fehler → reportError()

  3.2  fun splitPdf(record: ScanRecord, splitAtPages: List<Int>)
       ──────────────────────────────────────────────────────────
       - _editLoading = true
       - withContext(Dispatchers.IO):
           · pdfEditor.splitPdf(File(record.filepath),
                 context.filesDir.resolve("scans"), splitAtPages)
           · Für jede erzeugte Datei: generateThumbnail + ScanRecord anlegen
           · repository.saveScans(newRecords)
       - _success = getString(R.string.split_success, newRecords.size)
       - _editLoading = false
       - Fehler → reportError()

  3.3  fun reorderPages(record: ScanRecord, newOrder: List<Int>, saveAsCopy: Boolean)
       ──────────────────────────────────────────────────────────────────────────────
       - _editLoading = true
       - withContext(Dispatchers.IO):
           · resultFile = pdfEditor.reorderPages(File(record.filepath),
                 newOrder, saveAsCopy)
           · generateThumbnail(resultFile, thumbFile)
           · if saveAsCopy: repository.saveScan(neuer ScanRecord)
           · else:          repository.updateFileSize(record.id, resultFile.length())
             (isSearchable bleibt erhalten — PdfBox konserviert Text-Layer)
       - _success = getString(R.string.reorder_success)
       - _editLoading = false
       - Fehler → reportError()

SCHRITT 6 — SplitScreen (UPGRADE: voller Screen statt Dialog)
================================================================================

BEGRÜNDUNG: User weiß oft nicht, welche Seitennummer welchem Inhalt entspricht.
Ein Dialog mit reiner Zahleneingabe ist fehleranfällig. Standard in mobilen
PDF-Apps ist eine visuelle Thumbnailansicht mit wählbaren Trennpunkten.

  Neue Dateien:
    ui/split/SplitScreen.kt
    ui/split/SplitViewModel.kt

  Route: Screen.Split(route = "split/{scanId}") in Screen.kt

  SplitViewModel.kt:
    - Erhält scanId via SavedStateHandle
    - Lädt ScanRecord aus Repository (suspending, einmalig)
    - Rendert alle Seiten asynchron via pdfEditor.renderPageThumbnail()
      (Dispatchers.IO, eine nach der anderen, updatet pages-Liste inkrementell)
    - Exposiert:
        pages: StateFlow<List<PageThumb>>  — (index, bitmap?, isLoaded)
        splitPoints: StateFlow<Set<Int>>   — Indizes NACH denen getrennt wird
    - Methode: toggleSplitPoint(afterIndex: Int)
      (fügt hinzu oder entfernt aus splitPoints)
    - Methode: computePreview(): List<String>
      „Seiten 1–3 | 4–6 | 7" etc.
    - Methode: applySplit() → ruft homeViewModel.splitPdf() oder direkt
      pdfEditor + repository auf

  SplitScreen.kt:
    - TopAppBar: „PDF aufteilen – <Dateiname>" + Back + ✓ (enabled wenn ≥1 Splitpoint)
    - LazyColumn abwechselnd:
        [Seiten-Thumbnail (80dp breit)] + Seitennummer
        [Trennlinie mit Schere-Icon] — tippbar, wechselt Farbe wenn aktiv
    - Unten: Vorschau-Text „Erzeugt N Teile: Seiten 1–K | K+1–M | …"
    - Ladeindikator pro Thumbnail (CircularProgressIndicator) bis isLoaded
    - Beim Bestätigen: splitPdf aufrufen + zurücknavigieren

  Thumbnail-Rendering-Strategie:
    - Thumbnails werden sequenziell im Hintergrund geladen
    - UI zeigt Platzhalter (grauer Rahmen) bis Thumbnail fertig
    - Maximale Thumbnail-Größe: 120×170 px für Speichereffizienz
    - Thumbnails werden NICHT gecacht (nur für Dauer der Session im Memory)

SCHRITT 10 — Technische Hinweise und Risiken
================================================================================

  10.1 PdfBox-Speicher
       PDDocument muss immer in use{} (Kotlin) oder try-with-resources geschlossen
       werden. addPage() kopiert Seitenreferenz, keine Pixeldaten → für viele Seiten
       effizient. Input EINMAL laden und für alle Splits/Reorders nutzen.

  10.2 Thumbnail-Generierung — IO-Thread-Pflicht
       generateThumbnail() und renderPageThumbnail() MÜSSEN auf Dispatchers.IO
       laufen. PdfRenderer ist blocking I/O. Thumbnail nach Schreiben recyclen.
       PdfRenderer schließen bevor PdfBox dieselbe Datei öffnet (kein gleichz. Zugriff).

  10.3 Reorder + isSearchable — KEIN Reset nötig
       PdfBox konserviert das OCR-Text-Layer korrekt beim Verschieben von
       PDPage-Objekten via addPage(). isSearchable bleibt nach reorderPages() true.
       (Nur kritisch wenn Seiten neu gerendert werden — das passiert hier nicht.)

  10.4 FileProvider-Konflikt beim ATOMIC_MOVE
       Wenn die Zieldatei von einer externen App via FileProvider geöffnet ist,
       kann Files.move fehlschlagen. Fehlerbehandlung:
         catch (IOException) → temp löschen → reportError(R.string.edit_error_file_locked)
       Es gibt keinen zuverlässigen Pre-Check → try/catch ist der richtige Weg.

  10.5 BulkActionBar mit 6 Buttons
       Auf kleinen Screens (< 360 dp): Merge-Button in Overflow-Menü (DropdownMenu)
       auslagern, da Merge seltener benötigt wird als Share/Delete.

  10.6 Drag & Drop — sh.calvin.reorderable
       Bei Drag: haptisches Feedback via LocalHapticFeedback (HapticFeedbackType.LongPress)
       Up/Down-Pfeile als Accessibility-Fallback bleiben sichtbar (kein Verstecken
       bei Touch-Modus). Sorgt für Google Play Excellence-Konformität.

  10.7 WorkManager — Phase-2-Empfehlung
       viewModelScope ist für v1 ausreichend (konsistent mit OCR-Pattern).
       Bei Backgrounding bricht die Operation ab — Datei bleibt im Ausgangszustand
       dank ATOMIC_MOVE (keine halbfertigen Dateien).
       WorkManager als robuste Alternative für eine spätere Version einplanen
       (insbesondere für Merge großer PDFs > 50 MB).

  10.8 Keine Literalstrings
       Alle neuen User-facing Strings MÜSSEN über stringResource() /
       context.getString() eingebunden werden (Architektur-Regel).

  10.9 SplitScreen — Thumbnail-Memory
       Bei 50-seitigen PDFs: maximal 50 Bitmaps à 120×170 px ≈ 4 MB gesamt.
       Akzeptabel. Falls OOM: Thumbnails erst laden wenn Seite sichtbar wird
       (LazyColumn key-basiertes Lazy-Loading mit produceState).
